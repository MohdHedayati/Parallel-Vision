# Parallel-Vision

A C++17 image-processing library with **sequential, OpenMP, MPI and hybrid (MPI + OpenMP) backends** behind one API,
and a **dispatcher that picks the fastest backend** for the operation and image size.

Parallelism is not free: on a small image a parallel run can be dozens of times *slower* than a plain loop, and on a
large image a sequential run leaves the machine idle. Parallel-Vision measures where the break-even point is and uses it.

Operations: grayscale, Gaussian blur, Sobel, thresholding (incl. Otsu), and the full Canny edge detector.

**Authors:** Mohammed Mehdi Hedayati (241080023) and Nathan Julian Dsouza (241080016) —
Parallel Programming Laboratory, Semester 5 mini-project.

| | |
|---|---|
| Same output from every backend | OpenMP, MPI (1–8 ranks) and hybrid are bit-identical to sequential (tested) |
| Speedup (8 threads, Canny) | about 1.9–2.0× on large images (memory-bandwidth limited) |
| Automatic backend choice | within ~2 % of the best backend on average over 70 test cases; always-OpenMP is ~2× slower on average and up to ~87× slower on tiny images |

Full write-up with figures: [docs/Parallel-Vision-Report.docx](docs/Parallel-Vision-Report.docx).
All numbers are regenerated by one script (see [Reproducing the results](#reproducing-the-results)).

| Tool | Why | How to get it |
|---|---|---|
| MSYS2 (UCRT64) with g++, CMake, Ninja, OpenCV, MS-MPI | compiler (OpenMP), build, image file I/O, MPI headers/libs | `pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja mingw-w64-ucrt-x86_64-opencv mingw-w64-ucrt-x86_64-msmpi` |

Use the **MinGW** OpenCV from MSYS2, not the pre-built MSVC binaries (they are ABI-incompatible with g++).
The library itself does **not** depend on OpenCV; only the `pv` command-line tool and the OpenCV comparison benchmark do.

## 2. Build

```powershell
./build.ps1                       # OpenMP build (sequential + OpenMP backends)
./build.ps1 -DPV_WITH_MPI=ON      # also build the MPI backend, MPI tests and MPI benchmark
```

`build.ps1` puts `C:\msys64\ucrt64\bin` on `PATH`, configures CMake with Ninja in `build/`, and builds.
Executables and `libpv.dll` end up in `build/bin/`. To run them from your own shell, add
`C:\msys64\ucrt64\bin` to `PATH` first (so the MinGW/OpenMP/OpenCV DLLs are found).

| CMake option | Default | Meaning |
|---|---|---|
| `PV_WITH_MPI` | OFF | build the MPI backend (needs MS-MPI) |
| `PV_BUILD_CLI` | ON | build `pv.exe` and `pv_vs_opencv.exe` (need OpenCV) |
| `PV_NATIVE` | OFF | `-march=native` (faster, but the binary only runs on this CPU family) |
| `PV_WITH_CUDA` | OFF | reserved — **no CUDA code exists yet** |

## 3. Quick start

### Command line

```powershell
$env:PATH = "C:\msys64\ucrt64\bin;" + $env:PATH
build\bin\pv.exe canny     photo.jpg edges.png                    # Backend::Auto (dispatcher decides)
build\bin\pv.exe canny     photo.jpg edges.png --backend seq      # force sequential
build\bin\pv.exe canny     photo.jpg edges.png --backend omp --low 40 --high 120 --sigma 1.4
build\bin\pv.exe sobel     photo.jpg sobel.png
build\bin\pv.exe blur      photo.jpg blur.png --sigma 2
build\bin\pv.exe threshold photo.jpg bw.png --t otsu              # or --t 128
build\bin\pv.exe canny     photo.jpg edges.png --calibrate        # measure this machine, save pv_calibration.txt
build\bin\pv.exe canny     photo.jpg edges.png --use-calibration  # use the saved switch points
```

Each run prints the image size, the backend that was actually used, and the time.

### As a C++ library

```cpp
#include "pv/pv.hpp"

pv::Image img(width, height, 3);               // 8-bit BGR, fill img.data yourself (or via OpenCV, see cli/pv.cpp)

pv::Image edges = pv::canny(img);                                      // Auto: pv chooses
pv::Image a = pv::canny(img, 50, 150, 1.4, pv::Backend::Sequential);   // force a backend
pv::Image b = pv::canny(img, 50, 150, 1.4, pv::Backend::OpenMP);

pv::Backend which = pv::choose_backend(pv::Op::Canny, width, height);  // ask what Auto would do

pv::calibrate();                                  // optional: measure sequential vs OpenMP on this machine
pv::save_calibration("pv_calibration.txt");       // reload later with pv::load_calibration(...)
```

Link with CMake: `add_subdirectory(Parallel-Vision)` then `target_link_libraries(myapp PRIVATE pv)`.

### MPI (distributed memory)

`mpi_canny` is **collective**: every rank calls it; only rank 0's input is read and only rank 0 receives the result.

```cpp
pv::mpi_init(&argc, &argv);
pv::Image out = pv::mpi_canny(in, 50, 150, 1.4, pv::Backend::OpenMP);  // OpenMP inside each rank = hybrid
pv::mpi_finalize();
```

Run: `mpiexec -n 4 your_program.exe`. See `bench/mpi_bench.cpp` and `tests/test_mpi.cpp` for complete examples.

## 4. How it works

* **One kernel, several drivers.** Each algorithm is written once as a function over a range of rows. `for_rows()`
  runs it in a plain loop (Sequential) or under `#pragma omp parallel for` (OpenMP); the MPI backend runs the same
  kernels on each rank's strip. So results are identical by construction — and tested to be.
* **MPI strips with halo exchange.** Rank 0 scatters horizontal strips; neighbouring ranks exchange halo rows of
  depth `ceil(3σ)+2` (blur radius + gradient + non-max suppression); each rank computes its rows; compact edge labels
  are gathered on rank 0 for the global hysteresis step.
* **Dispatcher.** For `Backend::Auto`, OpenMP is chosen when `width × height ≥ N*(op)` (and more than one thread
  exists), otherwise Sequential. `N*` is a fixed 100 000 px by default (*heuristic*) or measured on your machine by
  `pv::calibrate()` (*calibrated*, per operation). MPI is never chosen automatically because it needs every process to
  take part — call it explicitly.

## 5. Reproducing the results

### One command

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_all.ps1            # builds, tests, benchmarks, makes figures
powershell -ExecutionPolicy Bypass -File scripts\run_all.ps1 -Image C:\path\photo.jpg -Reps 7
powershell -ExecutionPolicy Bypass -File scripts\run_all.ps1 -SkipBuild # reuse the existing build
```

Takes a few minutes. Everything lands in `results/`. For stable numbers: close other programs, plug in the laptop,
and run it twice — timings on a desktop vary by roughly 10–20 % between runs.

Then rebuild the Word report from those results:

```powershell
cd docs ; npm install ; node build_report.js        # -> docs\Parallel-Vision-Report.docx
```

### What each program measures

| Program | Run | Output |
|---|---|---|
| `pv_tests` | `build\bin\pv_tests.exe` | sequential == OpenMP for every operation; calibration round-trip; dispatcher rules |
| `pv_mpi_tests` | `mpiexec -n 4 build\bin\pv_mpi_tests.exe` (`PV_HYBRID=1` for MPI+OpenMP) | MPI result == sequential on several image shapes |
| `pv_bench` | `build\bin\pv_bench.exe 5 > results\bench.csv` | sequential vs OpenMP time, speedup, efficiency per image size |
| `pv_mpi_bench` | `mpiexec -n 4 build\bin\pv_mpi_bench.exe 5` | MPI time per size (`PV_HYBRID=1`, `OMP_NUM_THREADS=2` for hybrid) |
| `pv_dispatch_report` | `build\bin\pv_dispatch_report.exe 7 > results\dispatch.csv` | 70 cases: always-seq / always-OpenMP / heuristic / calibrated vs the oracle; calibrated switch points on stderr |
| `pv_vs_opencv` | `build\bin\pv_vs_opencv.exe 7 photo.jpg > results\vs_opencv.csv` | pv vs OpenCV Canny (1 and N threads); edge IoU on `photo.jpg` on stderr |
| `scripts\make_figures.py` | `python scripts\make_figures.py results` | all PNG figures and `summary.json` |

Reading the CSVs: `speedup = seq_ms / omp_ms`, `efficiency = speedup / threads`; in `dispatch.csv` the `oracle`
column is the faster backend in that case and `heuristic` / `calibrated` are what the dispatcher chose.

## 7. Limitations (short)

* **Not faster than OpenCV.** On a 4096² Canny, OpenCV needs about as long on *one* thread as pv does on eight, and is
  about 3× faster on eight. The contribution is the multi-backend design and the backend selection, not kernel speed.
* **Speedup saturates near 2×** on 8 threads: the passes are memory-bandwidth bound and hysteresis is partly serial.
* **MPI on one PC does not beat OpenMP** (shared memory bandwidth + scatter/gather copies); it was not tested on a cluster.
  Only Canny has an MPI path.
* **Calibration is not clearly better than the heuristic** on the test machine (both ≈ 1.02× average slowdown).
* **CUDA is not implemented.** MPI messages are limited to 2 GB per rank (int counts).
* One machine, one image family; run-to-run variation 10–20 %.
